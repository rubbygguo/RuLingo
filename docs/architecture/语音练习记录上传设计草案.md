# 语音练习记录上传设计草案

状态：草案 / 待讨论

这是一份待讨论设计文档，用于规划如何把每天语音练习后的结构化沉淀上传到 RuLingo 系统使用的 CloudBase MySQL 中。当前只做设计记录，不代表已经确定数据库结构或实现方式。

## 1. 背景

RuLingo 当前已经有远程数据能力：

- 前端通过 CloudBase JS SDK 连接 CloudBase。
- 当前已使用 MySQL 表记录每日任务完成情况。
- 已有表：`rulingo_daily_task_completions`。

接下来希望把每日语音练习的结果也沉淀到系统中，让 RuLingo 不只是显示任务完成情况，还能展示：

- 今天练习了什么内容
- 从练习中得到了哪些反馈
- 哪些地方需要加强
- 后续可以做哪些针对性练习
- 哪些表达值得复习

## 2. 当前设想的整体流程

```text
每日素材包生成
-> 用户复制语音陪练指令包到 ChatGPT
-> 用户完成语音练习
-> ChatGPT 输出反馈
-> 用户把反馈贴回 Codex
-> Codex 生成结构化沉淀
-> Codex 生成系统记录候选
-> 用户确认上传
-> Codex 运行本地 Node.js 上传脚本
-> 脚本写入 CloudBase MySQL
-> RuLingo 前端读取并展示
```

## 3. 为什么倾向于本地 Node.js 脚本上传

当前没有单独后端服务器，CloudBase MySQL 是主要远程数据层。

理论上有三种上传方式：

### 3.1 前端上传

优点：

- 用户点击按钮即可上传。
- 与现有 RuLingo 前端体验一致。

问题：

- 前端更适合处理轻量交互，不适合承担复杂解析、审核和数据迁移。
- 语音练习反馈来自 Codex 对话和本地 daily-pack 文件，前端未必能直接拿到这些内容。
- 上传前往往需要用户和 Codex 共同确认、修改、筛选。

### 3.2 本地 Node.js 脚本上传

优点：

- 适合读取本地 `materials-system/daily-packs/YYYY-MM-DD/` 中的结构化文件。
- 适合由 Codex 在用户确认后执行。
- 可以在上传前做校验、转换、去重、upsert。
- 不需要额外部署后端服务器。

问题：

- 需要设计好 CloudBase 连接方式。
- 需要明确当前用户身份 `user_id` 如何确定。
- 需要额外维护上传脚本和字段映射规则。

### 3.3 独立后端服务上传

优点：

- 长期最规范。
- 可以统一处理权限、审核、队列、日志。

问题：

- 当前阶段过重。
- 需要部署和维护服务器。
- 不符合现在“个人学习系统”的轻量需求。

当前倾向：

```text
短期：Codex + 本地 Node.js 脚本上传
长期：如果系统复杂度上升，再考虑独立后端
```

## 4. 每日工作区中的上传来源

上传的主要来源建议是：

```text
materials-system/daily-packs/YYYY-MM-DD/06-系统记录候选.md
```

辅助来源可能包括：

```text
04-练习反馈结构化沉淀.md
03-练习反馈原文_来源.md
02-语音陪练指令包_主题.md
```

其中：

- `03` 保存原始反馈，便于回溯，但不一定完整上传。
- `04` 用于指导后续素材生成。
- `06` 用于写入 RuLingo 系统记录。

## 5. 初步数据模型设想

### 5.1 最小可行版本：一张主表

表名暂定：

```text
rulingo_speaking_practice_records
```

可能字段：

```text
id
user_id
date_key
practice_type
scene
source_material
source_pack_path
target_expressions_json
practice_summary
feedback_summary
expression_issues_json
grammar_issues_json
fluency_issues_json
scenario_issues_json
reusable_expressions_json
next_practice_suggestion
skill_tags_json
raw_record_json
created_at
updated_at
```

说明：

- `target_expressions_json`：当天目标表达。
- `practice_summary`：练习内容摘要。
- `feedback_summary`：反馈摘要。
- `*_json` 字段用于先快速落地复杂结构，避免过早拆表。
- `raw_record_json` 保存完整结构化记录，方便以后迁移。

### 5.2 中期版本：主表 + 明细表

未来如果需要更细统计，可以拆成多表：

```text
rulingo_speaking_practice_records
rulingo_speaking_feedback_items
rulingo_expression_review_items
rulingo_next_practice_suggestions
```

可能用途：

- 按表达问题统计高频错误。
- 按能力标签生成复习任务。
- 单独追踪某个表达是否被复用。
- 在系统中展示“最近 7 天高频卡点”。

## 6. 上传脚本设想

脚本路径暂定：

```text
scripts/upload-speaking-record.mjs
```

使用方式可能是：

```bash
node scripts/upload-speaking-record.mjs 2026-05-12
```

脚本职责：

1. 读取指定日期的每日学习工作区。
2. 找到 `06-系统记录候选.md`。
3. 解析 Markdown 中的结构化内容。
4. 转换为数据库字段。
5. 校验必填项。
6. 连接 CloudBase MySQL。
7. upsert 到目标表。
8. 输出上传结果。

后续可能支持：

```bash
node scripts/upload-speaking-record.mjs today
node scripts/upload-speaking-record.mjs 2026-05-12 --dry-run
node scripts/upload-speaking-record.mjs 2026-05-12 --force
```

## 7. 需要讨论的关键问题

### 7.1 用户身份如何确定

当前前端登录使用用户名，并在任务完成记录中写入 `user_id`。

需要确定上传脚本如何知道当前用户：

- 从 `.env` 中读取固定 `RULINGO_USER_ID`
- 从 CloudBase 登录状态读取
- 从某个本地配置文件读取
- 上传时手动传参

待讨论。

### 7.2 CloudBase 连接方式

需要确认本地 Node.js 脚本如何连接 CloudBase MySQL：

- 是否复用 `@cloudbase/js-sdk`
- 是否需要额外服务端 SDK
- 是否需要 access key / secret
- 是否和前端 `UMI_APP_CLOUDBASE_*` 配置共用

待调研和验证。

### 7.3 数据表是否先一张表

短期推荐一张主表 + JSON 字段，降低实现复杂度。

但需要讨论：

- 是否方便前端展示
- 是否方便后续统计
- 是否会影响查询性能
- 是否未来迁移成本可接受

### 7.4 是否保存原始反馈全文

可选方案：

- 不保存原文，只保存结构化摘要。
- 保存原文到 `raw_record_json`。
- 原文只保存在本地 daily-pack，不上传数据库。

隐私和数据量都需要考虑。

### 7.5 上传触发方式

候选指令：

```text
上传今天的系统记录
上传 2026-05-12 的语音练习记录
先 dry-run 看看会上传什么
```

需要确定默认行为：

- 是否每次上传前都先展示预览
- 是否允许覆盖当天已有记录
- 是否支持撤销或重新上传

### 7.6 RuLingo 前端如何展示

可能新增模块：

```text
语音练习记录
口语反馈
需要加强
表达复习
下一次练习
```

待讨论展示粒度：

- 按天展示
- 按场景展示
- 按问题类型展示
- 按表达复习展示

## 8. 建议的下一步

暂时不实现上传脚本，先讨论并确定：

1. `06-系统记录候选.md` 的最终结构。
2. 最小数据库表字段。
3. 用户身份确定方式。
4. 上传时是否先 dry-run。
5. 前端最先需要展示哪些信息。

确认后再进入实现阶段：

```text
设计 SQL schema
-> 创建 CloudBase MySQL 表
-> 编写上传脚本
-> dry-run 验证
-> 上传一条测试记录
-> 前端读取并展示
```
