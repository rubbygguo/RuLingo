# 语言记忆库需求草案

状态：草案 / 待讨论

本文档记录 RuLingo 后续要建设的长期语言记忆功能。它暂时不命名为“生词本”，因为目标不是简单收藏单词，而是把用户在每日练习、Chat 对话和反馈中暴露出来的不熟悉词汇、短语、句型、搭配、语法点和个人错误，沉淀成可检索、可复习、可再次练习的学习资产。

## 1. 功能定位

语言记忆库是 RuLingo 的长期学习资产层，负责承接用户在学习过程中遇到的“不熟悉但值得掌握”的语言内容。

它应该支持：

- 记录：随时把词、短语、句型、搭配、语法点和错误记录下来。
- 复习：基于熟悉度、遗忘曲线和练习表现推荐复习内容。
- 翻阅：按标签、来源、主题、类型浏览历史积累。
- 查找：搜索英文表达、中文解释、标签、来源上下文和个人错误说明。
- 再练习：从已记录内容生成填空、造句、口语回答、听写或写作改写任务。

这个功能不应该变成普通收藏夹。每条记录进入系统时都应尽量结构化，并和来源、标签、复习状态、用户错误或上下文建立关系。

## 2. 记录入口

### 2.1 Chat 随手记录

用户可以在和 Codex 或 ChatGPT 对话时用自然语言要求记录，例如：

```text
把 take it for granted 记一下。
这个句型我不熟，加入记忆库。
记录一下我今天老是搞混的 assume / presume / suppose。
```

系统需要把自然语言请求整理成结构化内容，而不是只保存原文。Chat 中用户明确要求记录某个内容时，系统确认理解后直接写入正式记忆库，不需要 `pending` 状态。

记录项应尽量补全：

- 原始表达
- 内容类型
- 中文解释
- 英文解释
- 示例句
- 用户上下文
- 易错点或注意点
- 自动标签
- 来源
- 初始熟悉度
- 建议复习时间

### 2.2 DailyPack 复盘对话中记录

用户完成 DailyPack 的听、说、读、写练习后，可以把练习结果、回答或反馈发给 Codex。Codex 先基于用户表现推荐值得加入语言记忆库的内容，再和用户讨论删减、补充和确认。聊清楚后，确认项直接写入正式记忆库。

可记录来源包括：

- 听力 transcript 中值得掌握的表达。
- 阅读材料中的高价值词组、句型和搭配。
- 口语反馈中被纠正的表达。
- 写作反馈中反复出现的问题。
- 用户答错、没听懂、误用或无法主动输出的内容。

第一版不做页面手动加入，也不做自动待确认池。DailyPack 相关内容通过复盘对话确认后再入库。

### 2.3 推荐但不自动入库

系统可以在 DailyPack 复盘时推荐 Suggested Memory Items，但推荐本身不写库。只有用户明确确认要记录的内容才写入 `memory_items`。

推荐优先级：

- 用户明确答错或被纠正的内容。
- 同一问题多次出现的内容。
- 与今日主题高度相关的表达。
- 高频且可迁移到口语或写作的表达。
- 当前熟悉度低但复用价值高的句型或搭配。

这个规则用于避免把低价值内容批量堆入数据库：系统可以推荐，但数据库只保存确认后的 active 内容。

## 3. 内容单位

每条记录称为 `MemoryItem` 或 `LearningMemoryItem`。前端展示可以暂称为“Memory”或“语言记忆库”。

内容类型包括：

- `word`：单词。
- `phrase`：短语。
- `sentence_pattern`：句型。
- `collocation`：固定搭配。
- `grammar_point`：语法点。
- `pronunciation`：发音问题。
- `topic_expression`：特定主题下的表达。

用户错误不作为独立内容类型，而是作为某条内容下的 `mistakeNotes` 或来源上下文保存。这样核心内容类型保持干净，错误信息仍可用于搜索、复习和弱点分析。

单词形态不默认合并。用户实际记录的形式就是独立记忆项，例如 `take`、`takes`、`took`、`taken` 可以分别存在；如果需要关联，可以用 `base_form` 字段指向 `take`，但不自动合并熟悉度和复习状态。

后续如果与当前 DailyPack 的 `learningItems` 发生关系，需要明确两者边界：

- `learningItems` 是某个 DailyPack unit 内的当日学习点。
- `MemoryItem` 是跨日期、跨练习、可长期复习和检索的沉淀项。
- DailyPack 中的 `learningItems` 可以转化或关联到 `MemoryItem`，但不应自动全部进入长期库。

## 4. 标签和组织方式

标签应分层管理，避免只有自由标签导致数据库继续变散。

建议至少包含以下标签维度：

- 语言类型：word、phrase、pattern、grammar、pronunciation。
- 主题：technology、workplace、academic、travel、daily-life、news 等。
- 来源：chat、daily-pack、listening、speaking、reading、writing。
- 熟悉度：new、learning、unstable、familiar、mastered。
- 问题类型：meaning、usage、collocation、tense、preposition、pronunciation。
- 上下文：日期、DailyPack id、section、unit、原始材料或练习主题。

对用户展示时不必展示全部内部标签。页面应优先展示对浏览和复习有帮助的标签，例如类型、主题、来源、熟悉度。

## 5. 复习推荐

复习推荐应结合两条逻辑。

### 5.1 记忆强度驱动

每条记录应保存复习状态，例如：

- 当前熟悉度。
- 上次复习时间。
- 下次建议复习时间。
- 成功次数。
- 失败次数。
- 最近一次答题或输出表现。

系统每天可以推荐：

- 已到期复习的内容。
- 最近新增但仍不稳定的内容。
- 多次失败或多次被纠正的内容。
- 长时间未复习但曾经重要的内容。

第一版可以使用简单间隔规则，不必一开始实现复杂算法。

建议初始间隔：

```text
首次加入 -> 次日复习
第一次成功 -> 3 天后
第二次成功 -> 7 天后
第三次成功 -> 14 天后
失败 -> 次日或更短间隔
```

### 5.2 主题驱动

复习不应只按时间到期。系统还应结合今日练习主题或用户选择的 topic 推荐内容。

例如今日主题是 AI news，系统可以推荐：

- technology / news 主题下未掌握表达。
- 过去 DailyPack 中和 AI、工作、学术讨论相关的句型。
- 用户曾经在类似话题中误用的搭配或表达。

这能让复习和每日练习互相强化，而不是孤立背卡片。

## 6. 专门页面

RuLingo 需要一个专门页面承载该功能。候选命名：

- Memory
- Language Memory
- Language Vault
- Learning Library
- Review Hub

页面建议包含以下模块：

- Today Review：今日建议复习内容。
- Practice Review Suggestions：展示最近复盘中已确认加入或建议复习的内容，不作为待确认池。
- Browse by Tags：按类型、主题、来源、熟悉度浏览。
- Search：搜索表达、解释、标签和上下文。
- Weak Points：集中展示反复出错或仍不稳定的内容。
- Topic Review：按今日热点、今日练习主题或手动选择 topic 生成复习列表。

移动端、MatePad 和桌面端都需要支持。移动端应优先保证搜索、今日复习、按标签浏览三个核心流程紧凑可用；标签和筛选控件应尽量横向滚动，避免堆成很高的区域。

## 7. 最小数据库表设计

第一版不需要把例句、上下文、易错点、复习状态全部拆成独立表。为了支持搜索、标签筛选、去重和复习推荐，先使用两张表即可：

```text
memory_items
memory_item_tags
```

### 7.1 memory_items

`memory_items` 是主表，一条记录对应一个长期可复习的语言记忆项。

高频查询字段必须是单独列，不放在 JSON 里：

```sql
CREATE TABLE memory_items (
  id VARCHAR(64) PRIMARY KEY,
  owner VARCHAR(64) NOT NULL,

  type VARCHAR(32) NOT NULL,
  canonical_text VARCHAR(255) NOT NULL,
  display_text VARCHAR(255) NOT NULL,
  normalized_text VARCHAR(255) NOT NULL,
  fingerprint VARCHAR(255) NOT NULL,

  base_form VARCHAR(255) NULL,
  word_form VARCHAR(64) NULL,

  meaning_zh TEXT NULL,
  explanation_en TEXT NULL,

  familiarity VARCHAR(32) NOT NULL DEFAULT 'new',
  is_archived TINYINT(1) NOT NULL DEFAULT 0,
  next_review_at DATETIME NULL,
  last_reviewed_at DATETIME NULL,
  success_count INT NOT NULL DEFAULT 0,
  fail_count INT NOT NULL DEFAULT 0,

  source_kind VARCHAR(32) NULL,
  first_seen_at DATETIME NULL,
  last_seen_at DATETIME NULL,

  search_text TEXT NULL,
  details JSON NULL,

  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,

  UNIQUE KEY uniq_owner_fingerprint (owner, fingerprint),
  KEY idx_owner_type (owner, type),
  KEY idx_owner_base_form (owner, base_form),
  KEY idx_owner_familiarity (owner, familiarity),
  KEY idx_owner_archived_review (owner, is_archived, next_review_at),
  KEY idx_owner_next_review (owner, next_review_at),
  KEY idx_owner_last_seen (owner, last_seen_at),
  FULLTEXT KEY ft_memory_search (canonical_text, display_text, meaning_zh, explanation_en, search_text)
);
```

字段使用原则：

- `canonical_text`：用户实际记录的语言单位，例如 `taken`、`take it for granted`、`It is not that..., but that...`。
- `normalized_text`：用于基础去重的小写、空格归一化文本。
- `fingerprint`：去重指纹，例如 `word:taken`、`phrase:take_it_for_granted`、`pattern:it_is_not_that_x_but_that_y`。
- `base_form`：只用于搜索和关联，不用于自动合并。例如 `taken` 的 `base_form` 可以是 `take`。
- `search_text`：把例句、上下文摘要、易错点摘要等拼成可全文搜索文本，避免为了第一版搜索再拆更多表。
- `details`：保存暂时不需要独立查询的结构化补充内容，例如例句数组、上下文数组、易错点数组、AI 生成置信度。

### 7.2 memory_item_tags

标签需要支持筛选和组合查询，因此不要只放在 JSON 里。第一版可以不单独建 `memory_tags` 字典表，直接把标签关系压到一张表：

```sql
CREATE TABLE memory_item_tags (
  owner VARCHAR(64) NOT NULL,
  item_id VARCHAR(64) NOT NULL,
  category VARCHAR(32) NOT NULL,
  tag_key VARCHAR(64) NOT NULL,
  display_name VARCHAR(64) NOT NULL,

  PRIMARY KEY (item_id, category, tag_key),
  KEY idx_owner_category_tag (owner, category, tag_key),
  KEY idx_owner_tag (owner, tag_key)
);
```

例如：

```text
category=topic, tag_key=technology
category=source, tag_key=daily-pack
category=skill, tag_key=reading
category=problem, tag_key=preposition
```

这样可以支持：

- 按标签浏览。
- 多标签筛选。
- 今日 topic 复习推荐。
- 来源筛选，例如只看 DailyPack 或 Chat 记录。

### 7.3 搜索和去重策略

第一版搜索优先查：

- `canonical_text`
- `display_text`
- `meaning_zh`
- `explanation_en`
- `search_text`
- `base_form`
- `memory_item_tags.tag_key`

典型查询：

```sql
SELECT *
FROM memory_items
WHERE owner = ?
  AND (
    MATCH(canonical_text, display_text, meaning_zh, explanation_en, search_text)
      AGAINST (? IN NATURAL LANGUAGE MODE)
    OR base_form = ?
  );
```

按标签筛选：

```sql
SELECT mi.*
FROM memory_items mi
JOIN memory_item_tags mit ON mit.item_id = mi.id
WHERE mi.owner = ?
  AND mit.category = 'topic'
  AND mit.tag_key = 'technology';
```

如果同一个 `fingerprint` 再次出现，不新建 `memory_items` 主记录，而是更新：

- `last_seen_at`
- `source_kind`
- `search_text`
- `details` 中的上下文数组
- 相关标签

这保持了最小表数量，同时避免全表遍历和重复堆积。

## 9. 第一版范围

第一版目标是跑通一个小闭环，而不是一次性做完整知识图谱。

建议第一版包括：

1. 支持在 Chat 中明确要求记录某个内容，并直接创建 active MemoryItem。
2. 支持在 DailyPack 练习复盘对话中，由 Codex 推荐、用户补充确认后创建 active MemoryItem。
3. 入库前自动生成类型、解释、例句、标签、来源、搜索文本和复习时间。
4. 专门页面支持搜索、标签筛选、今日复习。
5. 每条记录支持“记住了”“还不熟”“生成练习”三类操作。
6. 根据操作结果更新熟悉度和下次复习时间。

当前已开始落地的第一步：

- 数据库建表 SQL：`docs/database/cloudbase-mysql-memory.sql`
- 本地上传入口：`npm run memory:upload -- --file=local-ops/memory-item.example.json`
- 示例输入：`local-ops/memory-item.example.json`
- 写入策略：根据 `owner + fingerprint` 查重；不存在则创建，存在则合并上下文、例句、易错点、标签和 `search_text`。

暂不作为第一版目标：

- 复杂知识图谱关系。
- 完全自动入库。
- 页面手动加入入口。
- pending / 待确认候选池。
- 精细化 SM-2 或类似记忆算法。
- 多用户共享库。
- 大规模统计报表。

## 10. 待确认问题

- 页面最终命名使用 Memory、Language Vault、Learning Library 还是中文名。
- MemoryItem 是否直接存入 CloudBase MySQL，还是先由本地脚本生成记录再上传。
- Chat 随手记录的上传动作由 Codex 本地脚本完成，还是未来由前端页面完成。
- DailyPack 复盘对话中，推荐哪些内容进入 MemoryItem 的判断规则如何稳定下来。
- 是否需要为每条记录保存原始上下文全文，还是只保存摘要和来源引用。
- “生成练习”第一版优先支持填空、造句、口语回答还是写作改写。
