# RuLingo 当前系统需求

状态：已确认 / 持续维护

本文档记录 RuLingo 当前已经确认的产品需求和系统能力边界。它不是每日素材生成规则，也不是具体数据库实现方案；它用于回答“这个系统现在应该支持什么能力、为什么这样设计”。

具体执行规则仍放在：

```text
materials-system/rules/
```

## 1. 系统定位

RuLingo 是一个个人英语学习系统，目标不是展示资料，而是支持长期输入、输出、反馈和复习沉淀。

当前系统重点支持：

- 每日学习计划。
- 每日素材包。
- 听、说、读、写四类学习 section。
- 素材、语言点、任务和反馈包的统一学习工作台。
- CloudBase MySQL 中的 DailyPack snapshot 读取。
- 用户练习后的反馈复制给 Codex，并由 Codex 继续整理沉淀。

## 2. DailyPack 当前能力

DailyPack 是每天的学习入口。它以数据库可渲染 snapshot JSON 的形式存在，由 `/daily-pack` 页面读取。

当前 DailyPack 应包含：

- `id`
- `date`
- `theme`
- `estimatedMinutes`
- `summary`
- `sections`
- `feedbackPackagePrompt`

当前 DailyPack 暂不要求包含：

- `targetExpressions`
- `expressionPool`

如果后续恢复表达池或长期表达复习系统，需要另行设计它和 `learningItems` 的关系。

## 3. Section 与 Unit

DailyPack 按听、说、读、写组织，每个 section 包含若干 unit。

每个 unit 是一个完整学习单元，当前核心结构为：

```json
{
  "id": "unit-id",
  "title": "Unit title",
  "tags": [],
  "instructions": "学习说明",
  "materials": [],
  "learningItems": [],
  "tasks": []
}
```

当前确认：

- `learningItems` 正式加入 unit 结构。
- `targetExpressions` 废弃。
- `expressionPool` 暂时隐藏和不生成。
- unit 标题在页面上以 `Unit 1`、`Unit 2` 这样的序号标识。

## 4. 听力 Section 改造需求

听力 section 的目标是帮助用户吸收 transcript 中真正有价值的语言点，而不是围绕 transcript 生成形式化习题。

当前听力 unit 应包含：

- 原始听力材料，例如音频/视频链接。
- transcript 或必要的文本材料。
- 从 transcript 提取的 `learningItems`。
- 每个 unit 一个自由反馈框。

听力 `learningItems` 必须有 transcript 证据：

- 每个 item 必须来自该 unit 的 transcript。
- 每个 item 必须提供 `sourceSentence`，且该句必须是 transcript 中真实出现的原句或连续片段。
- item 的 `text` 必须能在 `sourceSentence` 中直接找到；`listening_cue` 至少要有对应信号词或结构片段直接出现在 `sourceSentence` 中。
- 不允许根据主题、场景或常识自行编写“看起来相关”的表达。
- 如果 transcript 不可用，听力 unit 不应生成 learning items。

听力 `learningItems` 也不能只给少量几个显眼词敷衍了事。系统应认真通读 transcript，提取两类学习价值：

- 主题相关价值：与素材主题、场景、观点推进、关键信息理解直接相关的词、短语、句型和信号词。
- 语言资产价值：即使不只服务于本篇主题，本身也值得积累和迁移使用的地道表达、搭配、句型、口语结构、弱读/连读/缩略或易漏听表达。

目标不是把 transcript 变成完整词汇表，而是找出用户真正值得学、值得标记、值得反馈的语言内容。

当前听力 unit 不应包含：

- 传统 comprehension questions。
- 为了完成度而设计的形式化听力任务。
- `targetExpressions`。
- 复述支架。

听力 section 的 `tasks` 当前可以为空。听力语言点标记暂不计入完成度。

## 5. Learning Items

`learningItems` 是 unit 内可学习、可标记、可反馈的语言点。

当前字段暂定为：

```json
{
  "id": "li-keyword-1",
  "type": "keyword",
  "text": "fall behind",
  "meaning": "落后，跟不上",
  "sourceSentence": "I started to fall behind.",
  "note": "可以描述学习进度、项目进度或任务积压。"
}
```

当前支持的 `type`：

- `keyword`
- `phrase`
- `expression`
- `sentence_pattern`
- `listening_cue`
- `missed_sound`

暂不使用：

- `retell_frame`

每个听力 unit 的 learning item 数量暂不设置硬性上限，后续如果内容过重再限制。

## 6. 用户标记与反馈

用户可以对每个 learning item 做一个状态判断：

- `mastered`：掌握。
- `unfamiliar`：不熟。
- `ignored`：忽略。

用户也可以给单个 learning item 写备注。

当前不支持：

- `重要` 状态。
- `想复习` 状态。
- 结构化添加自定义语言点。

如果系统整理出的 learning items 没覆盖用户遇到的问题，用户通过 unit 自由反馈框补充。

## 7. Unit 自由反馈

每个 unit 底部提供一个自由反馈框。

用户可以写：

- 没听懂的词或短语。
- 系统漏掉但自己没掌握的表达。
- 自己不确定的句子。
- 对材料难度、速度或内容选择的感受。
- 想让 Codex 下次继续追踪的问题。

当前不做 section 级总反馈框，也不做“添加自定义语言点”的结构化入口。

## 8. 反馈包

反馈包用于把页面交互结果复制给 Codex，让 Codex 在对话中继续复盘。

当前反馈包应汇总：

- 已完成任务。
- 任务回答或输出文本。
- learning item 掌握状态。
- learning item 备注。
- unit 自由反馈。

当前反馈包不再汇总：

- 已勾选表达。
- `expressionPool` 勾选结果。

## 9. 重新生成与覆盖

DailyPack 支持重新生成并覆盖上传。

如果重新生成时本地已经存在当天 JSON，例如：

```text
data/daily-packs/YYYY-MM-DD.json
```

系统不应直接覆盖。Codex 必须先读取上一版内容，并向用户总结：

- 主题。
- 素材。
- section / unit。
- learningItems。

用户可以选择：

- 完全采纳上一版内容。
- 部分采纳上一版内容。
- 完全不采纳上一版内容。

Codex 应根据对话判断复用范围，再决定是否补充新主题、新素材或新语言点。只有确认复用策略和新生成方向后，才可以写入新版 JSON 并上传覆盖。

## 10. Mock Data 策略

改造需求阶段可以使用 mock DailyPack data 验证页面结构和交互。

当前确认：

- mock data 位于 `src/mockDailyPackData.js`。
- mock 模式当前已关闭。
- 后续如果继续使用 mock，应改成显式开发开关，避免线上误读 mock。

## 11. 待后续设计

仍需后续单独设计：

- 听力 section 的完成度模型。
- `learningItems` 是否扩展到阅读、口语、写作。
- 是否恢复 `expressionPool`，以及它和 `learningItems` 的关系。
- learning item 是否进入长期复习系统。
- learning item 标记和自由反馈是否写入 CloudBase。
- 系统如何根据用户“不熟/忽略/备注/自由反馈”自动调整后续每日包。
